# Задание 4 — HttpUnit

Программа из задания 4. К веб-приложению `my_app3` и к WildFly отношения не имеет,
запускается сама по себе, сервер поднимать не нужно.

Отчёт по заданию — `../docs/lab4-httpunit.md`.

## Что где лежит

```
HttpUnit/
├── src/               ОРИГИНАЛ как выдан преподавателем — не тронут
│   ├── Main.java          цикл запросов, setExceptionsThrownOnScriptError(false)
│   ├── HelloWorld.java    сервлет с опечаткой document.wr
│   └── com/…              исходники библиотеки HttpUnit (для чтения на защите)
├── src-demo/          копия оригинала для живого поиска утечки
│   └── Main.java          изменён один символ: sleep(200) → sleep(0)
├── src-fixed/         ИСПРАВЛЕННАЯ версия
│   ├── Main.java          + HttpUnitOptions.clearScriptErrorMessages()
│   └── HelloWorld.java    document.wr → document.write
├── tools/
│   └── Diag.java      замерочная программа (воспроизведение по требованию)
├── find-bug.bat       ЖИВОЙ ПОИСК утечки в VisualVM
├── demo.bat           ДОКАЗАТЕЛЬСТВО: три сценария подряд с цифрами
│
├── lib/, nbproject/, build.xml, manifest.mf   — из исходного архива
└── build/, patch/, gc.log                     — создаются автоматически
```

Оригинал в `src/` сохранён намеренно: по заданию нужно уметь воспроизвести поиск
проблемы по требованию преподавателя, а для этого баг должен остаться на месте.

## find-bug.bat — живая демонстрация в VisualVM

Два режима, оба запускают программу под маленькой кучей (`-Xmx16m`) в ускоренном
виде, чтобы разница была видна за минуту, а не за час:

```
find-bug.bat           запускает ОРИГИНАЛ — показываем утечку
find-bug.bat fixed     запускает с ИСПРАВЛЕННЫМ сервлетом — показываем, что её нет
```

Ускорение — ровно одна правка в `src-demo/Main.java`: `Thread.sleep(200)` заменён
на `Thread.sleep(0)`. Логика не меняется, меняется только темп запросов.
Совсем убрать строку нельзя — сломается компиляция, `catch (InterruptedException)`
станет недостижимым.

Важно: в обоих режимах работает **один и тот же** `src-demo/Main.java`, отличается
только сервлет, с которым он компилируется. То есть скорость, нагрузка и настройки
JVM одинаковые, и разница на графике объясняется исключительно исправлением.

Что делать после запуска: подключиться VisualVM к процессу `Main`
(Window → Applications → Local → Main) и пройти цепочку
Monitor → Perform GC → Sampler/Memory → Heap Dump → References.
Подробно расписано в `../docs/lab4-httpunit.md`, раздел 3.

Побочно пишется лог сборок мусора — запасное доказательство, если VisualVM подведёт.
Смотреть на число после стрелки, это занятая память сразу после сборки:

| Режим | Лог | Дно кучи через минуту | Сборок за минуту |
|---|---|---|---|
| оригинал | `gc.log` | 1 МБ → **14 МБ**, появляются Evacuation Failure | ~8 300 |
| `fixed` | `gc-fixed.log` | 1 МБ → 4 МБ и держится | ~2 600 |

## demo.bat — доказательство, что проблема устранена

Компилирует оригинал и исправленную версию, прогоняет три сценария, печатает
три таблицы. Занимает около минуты.

| # | Что запускается | Ожидаемый результат |
|---|---|---|
| 1 | оригинал, без очистки | `used` растёт линейно, `scriptErrors` = числу запросов |
| 2 | тот же баг в сервлете + `clearScriptErrorMessages()` | `used` выходит на полку, `scriptErrors` = 0 |
| 3 | исправленный сервлет (`document.write`) | `used` выходит на полку, `scriptErrors` = 0 |

Проверенный вывод на 10 000 запросов:

```
[1] iter=2000 delta=890 KB  … iter=10000 delta=2361 KB   scriptErrors=10000
[2] iter=2000 delta=601 KB  … iter=10000 delta=891  KB   scriptErrors=0
[3] iter=2000 delta=564 KB  … iter=10000 delta=894  KB   scriptErrors=0
```

Число итераций меняется строкой `set N=10000` в начале файла.

## Если JDK лежит не в `C:\Program Files\Java\jdk-17`

Оба `.bat` сначала ищут `javac` в `PATH`, и только потом смотрят по этому пути.
Если у вас другой JDK и его нет в `PATH` — поправьте три строки `set "JAVAC=…"`
в начале нужного файла.
