# Ответы на вопросы с лмс

---

## 1. Синхронная и асинхронная обработка HTTP-запросов. AJAX

**Синхронная обработка** — классическая модель «клиент-сервер» по схеме «запрос-ответ» (стр. 2, 5 лекции). Клиент отправляет HTTP-запрос и **блокируется**, ожидая ответа. В браузере это проявляется как перезагрузка страницы: пользователь нажал «Отправить» — страница ушла на сервер, сервер сформировал новый HTML, браузер его отрисовал. Пока ответ не пришёл, пользователь не может взаимодействовать со страницей. Минусы: долгое ожидание, мигание страницы, потеря состояния (введённых данных, положения скролла), лишний трафик (заново отдаётся вся страница, а не только изменившиеся данные).

**Асинхронная обработка** — запрос отправляется в фоне, страница **не перезагружается**, пользователь продолжает работать. Когда ответ приходит, JavaScript обрабатывает его и точечно обновляет нужный фрагмент DOM. Это основа современных SPA и «живых» интерфейсов.

**AJAX (Asynchronous JavaScript and XML)** — технология асинхронного обмена данными между браузером и сервером **без перезагрузки страницы**. Исторически название содержит XML, но сегодня данные чаще передаются в JSON, HTML или plain text. Реализуется через:
- `XMLHttpRequest` (классический, появился в 1999 г. в IE5);
- `fetch API` (современный, на промисах, встроен в браузеры начиная с 2015 г.);
- сторонние библиотеки (jQuery.ajax, SuperAgent, axios).

Схема работы AJAX:
```
Клиент (JS) --XHR/fetch--> Сервер
Клиент (JS) <--JSON/XML-- Сервер
   ↓
Частичное обновление DOM (без перезагрузки)
```

Ключевые свойства: асинхронность, работа в фоне, обмен **данными** (а не готовыми страницами), обновление только части интерфейса. В вашей лабораторной `index.js` использует `fetch` для отправки `action=check&x=...&y=...&r=...` и отрисовки результата в таблице.

## 2. Библиотека jQuery. Назначение, основные API

**jQuery** — кросс-браузерная JavaScript-библиотека, упрощающая работу с DOM, событиями, анимацией и AJAX. Появилась в 2006 г., когда браузеры сильно расходились в реализации JS-API; jQuery скрывал эти различия за единым интерфейсом. Сегодня, с унификацией DOM API и появлением `fetch`, jQuery используется реже, но в легаси-проектах встречается повсеместно.

**Основные API:**

| Категория | Методы | Назначение |
|-----------|--------|-----------|
| Селекторы | `$('css-селектор')`, `$('#id')`, `$('.class')`, `$('div > p')` | Поиск элементов по CSS-селекторам |
| DOM-манипуляции | `.html()`, `.text()`, `.val()`, `.attr()`, `.addClass()`, `.removeClass()`, `.append()`, `.remove()` | Чтение/изменение содержимого, атрибутов, классов, вставка/удаление узлов |
| События | `.on('click', fn)`, `.click(fn)`, `.submit(fn)`, `.change(fn)` | Подписка на события с делегированием |
| Эффекты | `.show()`, `.hide()`, `.fadeIn()`, `.slideToggle()`, `.animate()` | Анимация |
| AJAX | `$.ajax({...})`, `$.get(url, cb)`, `$.post(url, data, cb)`, `$.getJSON()` | Асинхронные HTTP-запросы |
| Утилиты | `$.each()`, `$.map()`, `$.extend()`, `$.trim()` | Итерация, слияние объектов, строковые функции |

**AJAX через jQuery** (пример):
```js
$.ajax({
    url: '/fcgi-bin/2lab.jar',
    method: 'POST',
    data: { action: 'check', x: 1, y: 2, r: 2 },
    dataType: 'json',
    success: (data) => renderTable(data.results),
    error: (xhr, status, err) => showError(err)
});
```

**Работа с DOM** — главная сила jQuery: цепочки вызовов (`.addClass('a').html('x').on('click', fn)`), автоматическая итерация по набору элементов, кросс-браузерность (в старых IE), удобные шорткаты. Пример из типичного проекта:
```js
$('#pointForm').on('submit', (e) => {
    e.preventDefault();
    $('#submitBtn').prop('disabled', true);
    // ...
});
```

## 3. Реализация AJAX с помощью SuperAgent

**SuperAgent** — небольшая JS-библиотека для HTTP-запросов в браузере и Node.js с **цепочным (fluent) API** и поддержкой промисов. Альтернатива `fetch` и `axios`, ценится за лаконичный синтаксис и удобную работу с формами, файлами, заголовками.

**Установка и подключение:**
```html
<script src="https://cdn.jsdelivr.net/npm/superagent@8/dist/superagent.min.js"></script>
```
или в npm-проекте: `npm install superagent`.

**Примеры использования:**

```js
// GET
superagent
    .get('/fcgi-bin/2lab.jar?action=list')
    .then(res => renderTable(res.body.results))
    .catch(err => showError(err));

// POST с form-urlencoded (аналог вашей лабы)
superagent
    .post('/fcgi-bin/2lab.jar')
    .type('form')                    // Content-Type: application/x-www-form-urlencoded
    .send({ action: 'check', x: 1, y: 2, r: 2 })
    .then(res => console.log(res.body))
    .catch(err => console.error(err.response?.body));

// POST с JSON
superagent
    .post('/api')
    .send({ x: 1, y: 2 })            // тип application/json выставится автоматически
    .then(res => res.body);

// Заголовки, куки, таймауты
superagent
    .get('/api')
    .set('X-Custom', 'value')
    .withCredentials()               // отправлять куки
    .timeout({ response: 5000 })
    .then(res => res.body);
```

**Ключевые особенности:** промисы (`then`/`catch`), автоматический парсинг JSON в `res.body`, цепочки, работа с multipart-формами (`attach()`), плагины, поддержка Node.js (можно использовать на сервере). По сравнению с `fetch`: не нужно вручную вызывать `res.json()`, автоматически бросается ошибка на `4xx`/`5xx`, проще отправка форм. По сравнению с jQuery: легче, только HTTP, без DOM-манипуляций.

## 4. Серверные сценарии. CGI — определение, назначение, ключевые особенности

**CGI (Common Gateway Interface)** — стандарт интерфейса между веб-сервером и внешней программой (скриптом), генерирующей динамический контент. Стандарт появился в 1993 г., спецификация — RFC 3875. Идея: сервер не умеет сам генерировать динамику, но умеет **запускать процессы** и передавать им данные через стандартные потоки.

**Назначение:** обработка форм, работа с БД, аутентификация, генерация HTML «на лету», любые задачи, требующие программирования, а не раздачи статики.

**Схема работы (классический CGI):**
```
1. Браузер: GET /cgi-bin/script.cgi?x=1&y=2
2. Apache получает запрос, видит путь /cgi-bin/, 
   запускает процесс script.cgi
3. Передаёт данные запроса через:
   - переменные окружения (REQUEST_METHOD, QUERY_STRING, 
     CONTENT_LENGTH, HTTP_*, SERVER_NAME, ...)
   - stdin (тело запроса, для POST)
4. Скрипт формирует ответ и пишет его в stdout:
   Status: 200 OK
   Content-Type: text/html
   
   <html>...</html>
5. Apache читает stdout, парсит заголовки, отдаёт клиенту
6. Процесс завершается
```

**Ключевые особенности:**
- **Process-per-request**: на каждый запрос — **новый процесс** ОС. Просто, изолированно, но дорого (fork/exec ~несколько мс на запрос).
- **Stateless**: между запросами ничего не сохраняется, каждый запуск — с чистого листа.
- **Языконезависимость**: скрипт на любом языке (Perl, Python, C, Java, bash), лишь бы читал stdin/env и писал в stdout.
- **Простота**: программа — обычный исполняемый файл, не нужны специальные библиотеки.
- **Безопасность**: изоляция процессов — плюс, но нужно аккуратно с правами и валидацией (CGI — классическая цель атак).
- **Проблемы**: медленно при нагрузке (много процессов), нет переиспользования соединений, нет пулинга, тяжёлая инициализация (загрузка JVM для каждого запроса — катастрофа).

Именно из-за этих ограничений появился FastCGI.

## 5. FastCGI — особенности технологии, преимущества и недостатки относительно CGI

**FastCGI** — развитие идеи CGI, устраняющее главный недостаток — запуск нового процесса на каждый запрос. Стандарт разработан в 1996 г. (Open Market), сегодня поддерживается Apache (mod_fastcgi, mod_proxy_fcgi), nginx, lighttpd, IIS.

**Ключевые особенности:**
- **Постоянные процессы (persistent)**: один процесс-обработчик (или пул) обслуживает **много запросов** подряд. Инициализация (загрузка JVM, соединения с БД, конфиг) выполняется один раз.
- **Демультиплексирование**: FastCGI-протокол бинарный, поддерживает несколько одновременных запросов через одно соединение (мультиплексирование по `requestId`).
- **Связь через сокет** (TCP или Unix domain), а не через stdin/stdout. Сервер и приложение — отдельные процессы, могут быть на разных машинах.
- **Процесс-менеджер**: FastCGI-приложение обычно управляется менеджером (php-fpm, spawn-fcgi, systemd), который держит пул воркеров и перезапускает упавшие.
- **Протокол**: бинарный, типизированные записи (`FCGI_BEGIN_REQUEST`, `FCGI_PARAMS`, `FCGI_STDIN`, `FCGI_STDOUT`, `FCGI_END_REQUEST`). Приложение читает stdin-поток, парсит параметры (аналог env CGI), пишет ответ в stdout-поток.

**Преимущества над CGI:**

| Критерий | CGI | FastCGI |
|----------|-----|---------|
| Процесс на запрос | Да (fork/exec) | Нет (переиспользование) |
| Время отклика | ~10–100 мс на запуск | ~1 мс (нет запуска) |
| Нагрузка на CPU | Высокая | Низкая |
| Память | Новая копия на запрос | Один пул воркеров |
| Инициализация (JVM, БД) | Каждый раз | Один раз |
| Масштабирование | Плохое | Хорошее (пул, отдельный хост) |
| Безопасность | Изоляция процессов | Изоляция процесса-воркера |

**Недостатки FastCGI:**
- **Сложнее настройка**: нужен менеджер процессов, конфиг, сокеты, права.
- **Сложнее отладка**: приложение — отдельный процесс, ошибки не в логах Apache, а в своих.
- **Stateful-риски**: воркер живёт долго, нужно аккуратно с глобальным состоянием (утечки памяти, «залипание» данных между запросами).
- **Управление пулом**: нужно правильно подобрать число воркеров (мало — очередь, много — память).
- **Проблемы с обновлением**: перезапуск воркеров без простоя требует graceful restart.
- **Безопасность сокета**: если FastCGI-порт открыт наружу (как у вас `*:24711`), в него можно стучаться в обход Apache — нужно биндиться на `127.0.0.1` или Unix-сокет.

## 6. FastCGI-сервер на языке Java

В Java FastCGI-сервер реализуется через библиотеку `fastcgi-lib.jar` (класс `com.fastcgi.FCGIInterface`). Она берёт на себя парсинг бинарного протокола FastCGI, а приложению остаётся читать параметры запроса и писать ответ в `stdout`.

**Минимальный сервер (как в вашей `Main.java`):**
```java
import com.fastcgi.FCGIInterface;

public class Main {
    public static void main(String[] args) {
        FCGIInterface fcgi = new FCGIInterface();
        while (fcgi.FCGIaccept() >= 0) {         // ждём запрос от Apache
            try {
                handle();                         // обрабатываем
            } catch (Exception e) {
                e.printStackTrace(System.err);
            }
        }
    }
}
```

**Как это работает:**
1. `FCGIaccept()` блокируется, пока Apache не пришлёт запрос по FastCGI-сокету (порт задан при запуске: `-DFCGI_PORT=24711`).
2. После accept параметры запроса доступны в `FCGIInterface.request.params` (это `java.util.Properties`) — аналог CGI-переменных: `REQUEST_METHOD`, `CONTENT_LENGTH`, `QUERY_STRING`, `HTTP_HOST`, `SCRIPT_NAME` и т.д.
3. Тело запроса (для POST) читается из `System.in` согласно `CONTENT_LENGTH`.
4. Ответ пишется в `System.out` — в формате HTTP-ответа (см. ниже).

**Формат ответа.** По умолчанию FastCGI-приложение шлёт **CGI-заголовки** (первая строка `Status: 200 OK`), и Apache (без `-nph`) сам преобразует их в `HTTP/1.1 200 OK`. Если в конфиге стоит флаг `-nph` (non-parsed headers), Apache передаёт байты **как есть** — и тогда приложение обязано само сформировать полноценную HTTP-статусную строку:
```
HTTP/1.1 200 OK\r\n
Content-Type: application/json; charset=utf-8\r\n
Content-Length: 71\r\n
\r\n
{...}
```
Именно поэтому в вашей `Response.java` первая строка должна быть `HTTP/1.1 %d %s\r\n`, а не `Status: %d %s`, если используется `-nph`.

**Запуск и связка с Apache:**
```bash
java -DFCGI_PORT=24711 -jar 2lab.jar           # приложение слушает порт 24711
```
```apache
FastCgiExternalServer ".../2lab.jar" -host localhost:24711 -nph
Alias /fcgi-bin/ ".../fcgi-bin/"
```

**Особенности Java-реализации:**
- Один JVM-процесс обслуживает много запросов → **нельзя хранить состояние между запросами в статических полях** (в вашей лабе `ResultStorage` — статический, это работает, но при перезапуске теряется; для реального приложения нужна внешняя БД).
- Многопоточность: `fastcgi-lib` обрабатывает запросы последовательно в одном потоке (в вашей `Main` — цикл `while`), что ограничивает пропускную способность. Промышленные решения используют пул потоков или несколько воркеров.
- Обработка ошибок: любое исключение в `handle()` должно быть перехвачено и превращено в корректный HTTP-ответ (у вас это сделано через `Response.error(500, ...)`).
- Логирование: `System.err` (идёт в лог FastCGI-процесса), `System.out` — только для HTTP-ответа (иначе сломается протокол).

# 20 дополнительных вопросов с ответами

## Лекция: HTTP, URI, REST

### 7. Что такое URI, URL и URN? В чём различие?
**URI (Uniform Resource Identifier)** — общий идентификатор ресурса, строка вида `<схема>:<идентификатор>`. **URL (Uniform Resource Locator)** — подмножество URI, указывающее **местонахождение** ресурса (`http://cs.ifmo.ru/spip.html`, `mailto:...`). **URN (Uniform Resource Name)** — подмножество URI, задающее **имя** ресурса без указания места (`urn:isbn:5170224575`). Все URL — URI, но не все URI — URL.

### 8. Структура HTTP-запроса.
1. **Стартовая строка**: `Метод URI HTTP/Версия` (`GET /spip.html HTTP/1.1`).
2. **Заголовки**: `ключ: значение`, по одному на строку (`Host:`, `User-Agent:`, `Accept:`, `Content-Length:` и т.д.).
3. **Пустая строка** (разделитель).
4. **Тело** (для POST/PUT — данные формы, JSON, файл).

### 9. Структура HTTP-ответа.
1. **Стартовая строка**: `HTTP/Версия КодСостояния Пояснение` (`HTTP/1.1 200 OK`).
2. **Заголовки** (`Server:`, `Content-Type:`, `Content-Length:`, `Last-Modified:` и т.д.).
3. **Пустая строка**.
4. **Тело** (HTML, JSON, бинарные данные).

### 10. Методы HTTP и их назначение.
- **OPTIONS** — узнать поддерживаемые методы/возможности сервера.
- **GET** — получить ресурс (без тела, параметры в URL).
- **HEAD** — как GET, но без тела ответа (только заголовки).
- **POST** — передать данные ресурсу (тело запроса), обычно создание/обработка.
- **PUT** — загрузить/заменить ресурс по указанному URI.
- **DELETE**, **PATCH** — удаление и частичное изменение (в лекции не упомянуты, но стандартны).

### 11. Классы кодов состояния HTTP.
Первая цифра — класс:
- **1xx** — Informational (информационные).
- **2xx** — Success (успех): 200 OK, 201 Created, 204 No Content.
- **3xx** — Redirection (перенаправление): 301 Moved Permanently, 302 Found, 304 Not Modified.
- **4xx** — Client Error (ошибка клиента): 400 Bad Request, 403 Forbidden, 404 Not Found, 405 Method Not Allowed.
- **5xx** — Server Error (ошибка сервера): 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable.

### 12. Что такое REST? Основные принципы.
**REST (Representational State Transfer)** — архитектурный стиль для сетевых приложений. Принципы: данные в стандартных форматах (HTML, XML, JSON); кэшируемость; независимость от сетевого слоя; **stateless** (сервер не хранит состояние между запросами); единообразный интерфейс (ресурсы идентифицируются URI, манипуляция через стандартные методы HTTP). Антипод — RPC (вызов удалённых процедур, например SOAP).

### 13. Что такое stateless-протокол? Как реализуются сессии?
**Stateless** — сервер не помнит предыдущие запросы; каждый запрос независим (HTTP — stateless). Сессии реализуются через **куки** (сервер ставит `Set-Cookie: sessionid=...`, клиент присылает его в `Cookie:`), либо через токены (JWT в заголовке `Authorization`), либо через скрытые поля форм / URL-параметры (реже).

### 14. Группы HTTP-заголовков.
- **General** — для запросов и ответов (`Cache-Control`, `Connection`, `Date`).
- **Request** — только в запросах (`Host`, `User-Agent`, `Accept`, `Referer`, `Cookie`).
- **Response** — только в ответах (`Server`, `Set-Cookie`, `Allow`, `Location`).
- **Entity** — описывают тело сообщения (`Content-Type`, `Content-Length`, `Content-Language`, `Last-Modified`).

## Лекция: HTML, DOM, JavaScript

### 15. Структура HTML-документа.
```html
<!DOCTYPE html>
<html lang="ru">
  <head>
    <meta charset="UTF-8">
    <title>Заголовок</title>
  </head>
  <body>
    <h1>Заголовок страницы</h1>
    <p>Абзац.</p>
  </body>
</html>
```
`<!DOCTYPE>` — версия HTML; `<html>` — корень; `<head>` — метаданные (кодировка, title, стили, скрипты); `<body>` — видимое содержимое.

### 16. Что такое DOM? Как с ним работать?
**DOM (Document Object Model)** — объектная модель документа: браузер парсит HTML и строит дерево узлов (элементы, текст, атрибуты). JS может читать и изменять это дерево, и браузер перерисовывает страницу. Основные методы: `document.getElementById`, `querySelector`/`querySelectorAll`, `createElement`, `appendChild`, `textContent`, `innerHTML`, `classList.add/remove`, `addEventListener`.

### 17. Что такое AJAX и как он реализуется через `fetch`?
AJAX — асинхронный обмен данными без перезагрузки. Современная реализация:
```js
const res = await fetch('/fcgi-bin/2lab.jar', {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded; charset=UTF-8' },
    body: new URLSearchParams({ action: 'check', x: 1, y: 2, r: 2 }).toString(),
    cache: 'no-store'
});
const data = await res.json();
renderTable(data.results);
```
`fetch` возвращает `Promise<Response>`; `res.json()` парсит тело как JSON; ошибки сети ловятся через `try/catch`, HTTP-ошибки (4xx/5xx) — проверкой `res.ok`.

### 18. Что такое CORS и зачем он нужен?
**CORS (Cross-Origin Resource Sharing)** — механизм, позволяющий браузеру делать запросы к **другому origin** (схема+хост+порт), чем у страницы. По умолчанию браузер блокирует такие запросы (same-origin policy). Сервер разрешает их заголовками `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`. В вашей лабе CORS не нужен: страница и FastCGI на одном origin (`localhost:8080`).

### 19. Селекторы и цепочки в jQuery.
Селекторы — CSS-подобные: `$('#id')`, `$('.cls')`, `$('div p')`, `$('input[name="r"]:checked')`. **Цепочки** — каждый метод возвращает тот же jQuery-объект, поэтому вызовы объединяются: `$('#x').addClass('a').val('1').on('change', fn)`. Внутри — набор элементов, методы применяются к каждому; `.end()` возвращает предыдущий набор.

## Лабораторная: CGI, FastCGI, Java-сервер

### 20. Как передаются параметры в CGI/FastCGI?
Для **GET** — в `QUERY_STRING` (часть URL после `?`), доступна как переменная окружения (CGI) или `params.getProperty("QUERY_STRING")` (FastCGI). Для **POST** — в **теле** запроса, длина в `CONTENT_LENGTH`, тип в `CONTENT_TYPE`; тело читается из `stdin` (CGI) или `System.in` (FastCGI). Формат `application/x-www-form-urlencoded`: `x=1&y=2&r=3`, значения URL-кодируются (`%20` для пробела и т.д.).

### 21. Ключевые переменные окружения CGI.
`REQUEST_METHOD` (GET/POST), `QUERY_STRING`, `CONTENT_LENGTH`, `CONTENT_TYPE`, `SCRIPT_NAME`, `PATH_INFO`, `SERVER_NAME`, `SERVER_PORT`, `SERVER_PROTOCOL`, `REMOTE_ADDR`, `HTTP_*` (заголовки запроса, например `HTTP_HOST`, `HTTP_USER_AGENT`, `HTTP_ACCEPT`).

### 22. Что такое URL-encoding и как он реализован в Java/JS?
URL-encoding (percent-encoding) — кодирование спецсимволов в виде `%XX` (пробел → `%20`, `&` → `%26`), чтобы они не ломали структуру URL/тела. Java: `URLEncoder.encode(s, StandardCharsets.UTF_8)` / `URLDecoder.decode(s, UTF_8)`. JS: `encodeURIComponent()` / `decodeURIComponent()`, а `URLSearchParams` кодирует автоматически при `toString()`.

### 23. Что означает флаг `-nph` в `FastCgiExternalServer`?
**NPH (non-parsed headers)** — Apache не парсит заголовки ответа, а передаёт клиенту **байты как есть**. Приложение обязано само сформировать полноценный HTTP-ответ, начиная со строки `HTTP/1.1 200 OK\r\n`. Без `-nph` приложение шлёт CGI-заголовки (`Status: 200 OK`), и Apache сам преобразует их в HTTP-статусную строку. Важно: в `-nph`-режиме разделитель строк — **CRLF** (`\r\n`), иначе клиент не распарсит ответ.

### 24. Почему FastCGI-приложение на Java должно быть потокобезопасным?
`FCGIaccept()` в цикле обрабатывает запросы в одном процессе; в многопоточных реализациях (или при пуле воркеров) несколько потоков могут одновременно обращаться к общим данным (статические поля, коллекции). Без синхронизации — гонки, повреждение данных. В вашей лабе `ResultStorage` — `ArrayList` без синхронизации, что допустимо при однопоточной обработке, но при переходе на пул потоков потребует `synchronized`/`ConcurrentHashMap`/`CopyOnWriteArrayList`.

### 25. Что такое Content-Length и почему он важен в ответе?
`Content-Length` — длина **тела** ответа в байтах. По нему клиент понимает, когда тело закончилось (особенно при keep-alive). Если указать неверно (меньше — обрежется, больше — клиент будет ждать), ответ сломается. В `Response.java` длина считается как `json.getBytes(StandardCharsets.UTF_8).length` — именно байты UTF-8, а не символы (кириллица занимает 2 байта в UTF-8).
